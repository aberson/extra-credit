Printable packets

Queue several generated worksheets — different types, variants and children — reorder them, give one sheet new problems, then preview and print the whole packet once, with the answer keys where you want them. The packet lives in its own private local file, so a reload or a server restart brings it back and never touches saved child profiles.

Why this shape

What the code survey found underneath printing today.

  • 1surface per browser print today: one worksheet or one key
  • 52,491 bytesten of today's largest documents, compact, against the profile file's 65,536-byte cap
  • 256 KiBthe packet file's own cap, with the worst ten-sheet packet held under half
  • 48assumption rows re-checked against shipped code before Step 28

Printing is one surface at a time

PrintView shows one worksheet or one key and calls the browser print for that one surface, and the named page comes from that surface's own paper. A packet therefore needs its own composed print view — one page per surface, a page break between them — not a loop that calls Print again. Single-sheet printing, its print CSS and its renderers stay exactly as proven.

A second file, not a key in the profile file

Ten of the largest documents already take most of the profile file's cap, and a key there would force a profile schema version 3 and tie packet recovery to profile recovery. So the packet gets its own sibling file, built on the same extracted file-safety code, and neither store ever reads, locks or backs up the other's file.

Stored pages, proven on every load

The file treats each document as opaque; the browser proves each sheet by regenerating it from its own stored request. A later generator, family or request change never invalidates the file — it only flags the sheets it touches, which keep their stored bytes and can be removed or given new problems.

Look at these first

Three defaults with the biggest effect on you.

Everything else can wait for a skim. These set the packet's shape, how you match keys to pages, and what happens to a child's queued sheets when you delete the child.

D-packetTen sheets, one layout, keys at the end

At most 10 sheets, one paper size and print scale for the whole packet, keys grouped at the end by default, sheets for different children allowed, and printing never clears the packet. A layout change keeps a sheet's problems only when its generator produces the identical items at the new layout; any other sheet is named and changes only when you choose Make new problems, which Undo covers.

D-packet -> allow 12 sheets

D24Keys are labeled; child pages are not

Each key heading names its sheet, family and printed nickname, but child pages gain no label, because an extra line would change page geometry the single-sheet print matrix proved. With keys grouped at the end, two sheets that print the same title match their keys only by order and problems; the panel then recommends Each key after its worksheet. M1 and M2 observe it.

D24 -> label child pages too

D26Deleting a child keeps its queued sheets

Deleting a profile never rewrites the packet. That child's sheets stay, labeled "for a removed profile", with the profile id and any printed nickname they were made with, until you remove them. The delete dialog says how many stay — or, while the packet is loading or cannot be opened, that it may still hold some — and the privacy docs give cleanup guidance.

D26 -> offer to remove those sheets with the profile

Four open questions, each answered by a default

The plan answers every question it raised, so silence lets the build proceed. Reply only to change one:

  • Several named packets? No — one current packet (D10); named packets need a packet schema version 2.

Risks worth knowing

What could bite, and the built-in answer.

  • A step runs out of its three iterations, and the halt parks everything after it (P7).D50 rebalanced the load across Steps 28–34; the durable file, store and API land first, so any halt leaves a durable, non-destructive state. No budget extension.
  • The shipped plans 01 and 02 differ from what this plan assumes.The pre-build delta check re-runs 48 rows against the shipped code before Step 28; a failed gating row parks this plan for redline instead of building on a wrong assumption (D51, D53).
  • You match a grouped key to the wrong child page.Key headings name sheet, family and printed nickname and follow sheet order; the same-title note recommends Each key after its worksheet; M1 and M2 observe the accepted limitation (D24).
  • A deleted child's nickname and id stay in queued sheets and packet backups.Rows say "for a removed profile", the delete dialog states the count or that sheets may remain, removal is explicit, and the privacy docs give cleanup guidance (D26, Step 34).
  • A later generator change makes an old sheet unreproducible.Only that sheet is flagged; it keeps its stored problems and can be removed or given new problems. The file itself never becomes invalid (D9, D46).
  • Two tabs edit the packet at once.ETag preconditions: the second save conflicts, reloads once and says so, and Undo is offered only while the saved packet is the one its action produced (D17, D18).
  • A hand-edited or hostile packet file.Nesting depth and every numeric capability are bounded before any generator runs; an over-deep file reaches backup-first recovery rather than a permanent error (D39, D54).
  • A labeled key page overflows at maximum length.Step 33 measures every labeled key page on both papers and scales; one label-only style remedy is pre-authorized (D25).
  • A runtime reviewer leaves a fictional packet file in the main checkout.It is gitignored and export-excluded from Step 28, reported by name and left for you; the panel stays hidden unless such a file exists (D-pregate, D28).
  • The retained UAT launcher's working directory gains a packet file its mirror does not copy.PK-0 is your private decision before using packets with it; agents never read the launcher (D-uatbackup).
  • A resumed run after a halt meets a real profile file you restored.Pre-run items 1–3 hold again before any resumed or re-armed run of this plan, as metadata-only checks (D-pregate).
