## 1. What This Feature Does

Proposal: documentation/worksheet-first-proposal.html (plan-redline publication 2, 2026-09-29; a standalone offline view of this plan, which remains the source of truth)

A parent chooses the work first: worksheet type, its variant, the child, then an explicit **Practice focus** that states its operations and range. Today's exercise no longer requires editing a child profile. It is built because UAT found that `projectGenerationRequest` copies the writing mode, presentation band and every math maximum from the stored profile (`src/shared/worksheet/project-request.ts` :221); that Difficulty silently rescales those maxima by ×0.75 or about +25% (`applyDifficulty` :84) and, for Two Whats and a Wow, switches an equation-capable child to quantity mode (`src/worksheets/find-the-wow/definition.ts` :94); and that decorative art depends on an unrelated content checkbox.

Child profiles shrink to identity (optional nickname, review date, up to five interests) and age is removed entirely (P2). Worksheet choices live in session state and are saved only as one global `defaults` object, only by the existing explicit "Save these as worksheet defaults" action (P1). Because the persisted shape changes, the local config moves to a real `schemaVersion: 2`: a v1 file is read without being written, the first explicit save upgrades it after writing a byte-identical copy of the v1 file, newer versions stay blocked, and recovery still backs up first. Each child's earlier writing mode, vocabulary band and math values are kept read-only and seed that child's choices until the parent's first explicit defaults save ends seeding permanently (D10).

### Parent-visible contract

Tests cite these IDs.

| ID | Contract |
|---|---|
| U1 | **Worksheet type is the first and largest choice.** It is a radio-card group named "Worksheet type" listing the four families, each with a one-line description, in a responsive grid that stacks at 320 CSS px. |
| U2 | **The variant comes next, where one exists.** Sentence Builder has "Writing activity": Draw & Tell, Picture Labels, Copy a Sentence, Finish a Sentence, Independent Writing. Two Whats and a Wow has "Statements": Quantity pictures or Equations. |
| U3 | **Then the child.** Each child appears by nickname, or as "Profile N" if it has none. No age appears anywhere except the one-time upgrade notice (U11), and a child never controls availability. |
| U4 | **Then the practice focus, in words.** Math labels state the operations and range, for example "Addition within 20", "Addition and subtraction within 100" or "Quantities to 10". Sentence Builder shows "Vocabulary" with the two option labels DD12 states exactly. There is no Difficulty control and no multiplier: the request carries exactly the stated range. |
| U5 | **A summary and Create close the primary block.** Blocking guidance sits directly above Create, outside More options, and Create's `aria-describedby` points at it. |
| U6 | **More options holds only secondary choices:** Length (with the count for each length), the answer key, a Personalization group (nickname, reviewed interests, decorative graphics, and Theme from Step 19) and the Print layout group (paper, scale). |
| U7 | **A changed choice never leaves a stale preview.** Inapplicable controls are absent, and another family's settings never change this family's request. |
| U8 | **Selections are session state.** They survive profile edits, profile saves, cancelled edits and in-app config reloads (the "Reloading saved profiles" path after an ETag conflict or another tab's save). A browser page reload restores only the saved defaults, because no browser storage is used. Create never writes the file; only "Save these as worksheet defaults" writes worksheet choices. |
| U9 | **Earlier settings carry over visibly.** While seeding is on, any choice the parent has not changed follows the selected child's earlier settings. A status line names what was used and any value that was clamped. The save slot explains that saving defaults ends seeding permanently; no control turns it back on (D10). |
| U10 | **The artwork Theme is explicit (Step 19):** From interests, Animals, Space, Nature, Sports, Vehicles or Neutral. A theme never changes the work or the answers. |
| U11 | **Upgrades are announced, never silent.** A v1 file loads with a notice, and reading never writes. The next save keeps a byte-identical copy of the earlier file. A newer-version file stays blocked and untouched. |
| U12 | **Accessibility holds.** Keyboard-only creation works with visible focus. The page reflows at 320 CSS px without horizontal scroll, and labels survive 200% text. The six declared WCAG tag groups report zero axe violations. Help text says the worksheets are designed for early primary practice. |

A successful profile add, edit or delete dispatches `profilesChanged`; a successful defaults save dispatches `defaultsSaved`; the child select dispatches `childSelected`; every other panel control dispatches `changed`.

## 6. Design Decisions

**DD1. A real schema version with a frozen v1 read path (D-schema, D30).**
- **Why a bump:** Adding fields to v1 in place is unsafe. A shipped build classifies any v1 object it cannot strictly parse as `CONFIG_INVALID`, then offers backup-and-replace, which rewrites the file as defaults plus one profile (surprise 3). A real `schemaVersion: 2` makes every older build classify the file as future (`> 1`) and block with `CONFIG_VERSION_UNSUPPORTED`. The block is visible but non-destructive.
- **How:** Step 14, a pure refactor with no persisted-shape change (D-split), moves the v1 schemas unchanged into `legacy-v1.ts` with `z.literal(1)`, and the shared enum arrays and field building blocks into the leaves `enums.ts` and `fields.ts` (D30), so `legacy-v1.ts` never imports `schema.ts` and module evaluation has no cycle. Step 15 adds v2, and `isFutureVersion` then compares against `APP_CONFIG_SCHEMA_VERSION`.
- **Rejected:** Optional compatibility fields inside v1, because of the older-build hazard.

**DD2. Reading never writes; the first explicit save upgrades (D15).**
- **Reads:** `GET` on a valid v1 file migrates in memory and returns `{ config, storedSchemaVersion: 1 }` with the ETag of the raw v1 bytes. The file is not touched.
- **The upgrade:** Any explicit `PUT` whose `If-Match` equals that ETag (a profile add, edit or delete, or a defaults save) runs the serialized-size check, then writes `children.local.json.v1-<YYYYMMDDTHHMMSSZ>-<8hex>.bak` byte-for-byte through the existing exclusive routine (generalized to `#writeBackup(bytes, prefix)`: `wx`, mode 0600, fsync, at most eight attempts under `RECOVERY_ATTEMPT_LIMIT`, so seven `EEXIST` retries), then performs the atomic v2 replace.
- **Failure paths:** Oversize fails with 413 and creates no backup: `CONFIG_SERIALIZED_TOO_LARGE` when the store's pretty-printed v2 bytes exceed 65,536, or `BODY_TOO_LARGE` when the request body itself exceeds Fastify's `bodyLimit` first. Either way the bytes are unchanged. A backup failure fails with 503 `CONFIG_IO_ERROR` and leaves the target unchanged.
- **After the upgrade:** Later saves see a v2 file and write no further backup. P2's "the v1 backup retains the old value" is exactly this file.
- Appendix B.2 lists every create, edit, reload, recovery, newer-version, older-build and stale-tab path.

**DD3. The final persisted shape lands whole and is pinned in Step 15 (D9, D-split).**
- **Why:** Under P7 a halt can leave an interim local `main`. It is never launched against real data (pre-run item 4), but the file any interim code could write must be either the unchanged v1 shape (a halt after Step 14) or the final v2 shape (from Step 15), so no later step needs another migration.
- **How:** `config-shape-fingerprint.test.ts` (Step 15) pins the full persisted value domain the same step lands, not only key names. Comparing the snapshot with Appendix A is a review aid only; DONE rests on the test and its calibration variants (D-scripted-evidence). It snapshots, sorted, the composed v2 transport JSON Schema: every key path, `required` list, `enum` member, `const`, `minimum`/`maximum`, `minItems`/`maxItems`, `uniqueItems` and `additionalProperties: false`. It also snapshots the sorted names of every Zod refinement on a persisted object, which `schema.ts` registers in an exported `PERSISTED_REFINEMENTS` list. It must pass unchanged at Steps 16–20.
- **Text bounds:** the text bounds (`displayName` 1..40 and each interest 1..32 code points after normalization, at most five interests) live only in Zod; the transport schema leaves them to Zod (`transport-schemas.ts` :136, :184). The fingerprint therefore also pins them behaviorally: it parses each text field at its maximum and at maximum + 1 code points through `AppConfigV2Schema` and snapshots the outcomes.
- **What fails:** adding a key, adding or removing an enum member (for example widening `MATH_OPERATIONS` or `THEME_CHOICES`), moving a JSON-Schema bound or a text bound, or adding, removing or renaming a registered refinement. Each fails with "Changing the persisted config shape requires schemaVersion 3 with a v2 read path".
- **Why values too:** an older v2 build classifies a same-version file it cannot strictly parse as `invalid` (`config-store.ts` :417-420) and offers backup-and-replace, which is the destructive path DD1 exists to prevent.
- **Contributing rule:** in Step 15, `CONTRIBUTING.md` gains a "Persisted shape" rule covering any change to accepted keys or accepted values. Plans 02 and 03 therefore bump to v3 with a v2 read path if they persist anything new or widen anything persisted. The rule also states the limits: `PERSISTED_REFINEMENTS` is a hand-kept list that pins names, not logic, so a new refinement that is not registered, or a change inside a named refinement, is left to review, and every new refinement on a persisted object must be registered.
- **Rejected for now (redline option):** a classifier that blocks, instead of invalidating, a same-version file whose only failures are unknown enum members. The fingerprint and the v3 rule already keep such a file from being written.

**DD4. Recovery keeps its mechanics and states what it drops (D14; surprise 4).**
- **Decision:** Recovery still writes the byte-identical `.invalid-…bak` first, then replaces the file with `emptyAppConfigV2()` plus the one draft profile. The client never receives invalid bytes, so it cannot rebuild more.
- **Disclosure:** `RecoveryPanel` now states before confirmation that every other profile, the saved worksheet defaults and all earlier settings remain only in the backup file. Its download copy stops naming age.
- **Rejected for this plan:** Per-record server-side salvage. It adds a new data path (profile data in an error body) and scope that neither the seed nor the operator asked for. It is recorded as a redline option.

**DD5. Config API contract (D11, D15).**
- `GET /api/config` returns 200 `{ config: AppConfigV2, storedSchemaVersion: 1 or 2 }` with the raw-byte ETag. Other outcomes: 404 `CONFIG_NOT_FOUND`; 409 `CONFIG_INVALID` with ETag; 409 `CONFIG_VERSION_UNSUPPORTED` with ETag for any integer `schemaVersion > 2`.
- `PUT` accepts only a v2 body (`schemaVersion: { const: 2 }`). A v1-shaped body gets 422 `VALIDATION_FAILED`, which covers a stale tab running an older bundle. Preconditions, the recovery header and the status map are unchanged.
- **Error codes:** no new public codes. `GENERATION_AGE_UNSUPPORTED` is retired; the in-browser projection was its only producer. 20 codes remain.
- **Consumers of the new body field:** `storedSchemaVersion` is an intended wire change. Every consumer is audited in Step 15: `client.ts`, `config-api.test.ts` :215, `print.spec.ts` :1132, and the mocked config API in `ProfileEditor.test.tsx` (`configResponse`, :81-86, which returns only the config and backs every App-level case).

**DD6. Transport parity by construction (D9; surprise 5).**
- **Decision:** `transport-schemas.ts` imports the `as const` enum arrays and the ceilings `V1_NUMERIC_MAXIMUM` and `DRY_MATH_NUMERIC_MAXIMUM` instead of restating literals. The legacy `mathSkills` block keeps its 0–1,000 bounds.
- AJV stays transform-free, and Zod stays authoritative for text normalization and cross-field rules.
- **Parity test:** it asserts each transport enum `toBe` its Zod array. It checks every member and one non-member, and every numeric bound at min−1, min, max and max+1. It requires a parity row for every key path the fingerprint lists.
- **Rejected:** Zod 4's `z.toJSONSchema`, which cannot express the text transforms.

**DD7. The privacy audit follows the shape (D17; surprise 6).**
- **Detector keys:** The audit detects records by `id`, `reviewedOn` and `interests`, the keys every v1 and v2 profile must carry. This is a strict subset of today's seven keys, so detection only broadens.
- **Hash allowance:** It stays whole-record.
  - Step 14 adds the example's committed LF blob as `frontend/tests/fixtures/config/children.v1.json`, with the same record hashes (D32); from Step 15 the example stays byte-identical, still v1, read through migration.
  - Step 18 converts the example to identity-only v2 and adds exactly three v2 hashes, six in total.
  - Plan Appendix 12.1 stays v1 and permitted.
- **README terms:** "4–8" and "9–18" become "early primary" in Step 18, in the same diff as the README edit (D-split tweak).
- **Fixtures:** Migration tests build non-canonical fictional records at runtime. No committed file gains a v2 record carrying `legacyChoices`; the expected upgraded bytes are pinned as a SHA-256 digest instead, in `tests/integration/migrate-fixture.test.ts` (§5 defines the digest).

**DD8. Global defaults and session state (P1, D20, D25; surprise 10).**
- **Shape:** The top-level key stays `defaults`; a rename would only add churn. It holds the whole `WorksheetDefaultsV2`: worksheet type, per-family focus, variants, vocabulary, theme, layout and personalization, plus `useEarlierChildSettings`.
- **Who writes it:** Only "Save these as worksheet defaults" writes it, as the existing `defaults` operation kind, with `profiles` passed through untouched. Create and Make another never write.
- **Session state:** The current selection is App state (`useReducer`) created from `defaults` on the first ready load. Because it lives above the editor ternary and the revision key is deleted, profile edits, saves, cancels and in-app config reloads keep unsaved choices. A browser page reload restores only the saved `defaults`, and no browser storage is added (U8).
- **In-app config reloads:** a reload through the "Reloading saved profiles" path (an ETag conflict, or another tab saved) that brings changed `defaults` moves only the groups the parent has not touched.

**DD9. Earlier settings seed untouched choices until the first explicit defaults save (D-schema, D10, D21, D-interim, D-save).**
- **What migration keeps:** Migration moves each v1 profile's `presentationBand`, `writingMode` and full `mathSkills` verbatim into a read-only `legacyChoices`. Custom values, maxima above activity ceilings and the dormant permission flags all survive.
- **Seeding rule:** While `defaults.useEarlierChildSettings` is on, every control group the parent has not touched this session shows the selected child's earlier value (Appendix B.3). A child without earlier settings shows the saved default. Touched groups never move on a child switch.
- **Status line:** It names what was used and lists clamped values (for example "stored 50, using 20") and stored-but-unused permission flags. This keeps Step 9's disclosure behavior.
- **The defaults-save rule (D-save).** This is the one statement of what "Save these as worksheet defaults" writes; every step, test and appendix row cites it rather than restating it.
  - *Before the panel (Steps 15–16):* the interim save writes only the layout and personalization fields the UI shows, with `theme` derived per D33, and passes every worksheet group and `useEarlierChildSettings` through unchanged, so it never writes a group derived from a child's earlier settings (tested at App level in `ProfileEditor.test.tsx`, the web test that renders App over a mocked config API, in Steps 15 and 16). Step 14 changes no save.
  - *Once the panel exists (Step 17 on):* the save writes exactly the visible selection, seeded groups included, as the whole `defaults` object with `useEarlierChildSettings: false` (tested at App level in `ProfileEditor.test.tsx` in Step 17, replacing the interim case). The parent saves what they see, those values become the global starting choices for every child, nothing visible changes at the save or after a reload, and the values stop being per-child the moment they are saved. While seeding is on and some profile carries `legacyChoices`, the save slot shows the note "Saving makes these the starting choices for every child. Children's earlier settings stay in the file but will no longer be used as starting points."
  - *Seeding ends at the first explicit save:* no control or code path sets the flag back to true, and no re-enable control ships. A parent who wants a child's earlier choices picks them in the controls before saving. Stored `legacyChoices` are retained, never deleted. Seeding therefore only supplies each child's initial choices, as D-schema allows, and after the parent sets global defaults no per-child attribute drives any choice (P1).
- **Flag values:** Migration sets the flag on when the v1 file had profiles; a fresh install starts off.
- **What never happens:** No UI edits `legacyChoices` after Step 18, and nothing deletes it: there is no forget action until a documented compatibility policy exists.
- **Interim editing (Steps 15–17, D-interim):** The unchanged profile editor still writes `legacyChoices` for new profiles, so every intermediate step stays usable and fully gated without a second schema change.
  - Interim-created `legacyChoices` are indistinguishable from migrated ones, and from Step 18 they are treated identically (D21). They stop influencing choices at the first explicit defaults save.

### B. Migration and storage behavior

**B.1 v1 → v2 field mapping**

| v1 field | v2 destination |
|---|---|
| `schemaVersion: 1` | `schemaVersion: 2`, written only by the first explicit save |
| profile `id`, `displayName`, `reviewedOn`, `interests`, and profile order | unchanged |
| profile `ageYears` | absent from the live file; kept in the `.v1-…bak` (P2) |
| profile `presentationBand`, `writingMode`, `mathSkills` | verbatim in `legacyChoices` |
| `defaults.useDisplayName`, `useInterests`, `includeDecorativeGraphics`, `length`, `includeAnswerKey`, `paperSize`, `printScale` | the same names in `defaults` |
| `defaults.difficulty` | absent (the concept is removed) but kept in the backup; the upgrade notice says Practice focus replaced it and that a saved Confidence or Stretch no longer applies |
| (none) | `theme = useInterests ? "from-interests" : "neutral"`; `useEarlierChildSettings = profiles.length > 0`; every other new field from `DEFAULT_WORKSHEET_DEFAULTS_V2` |

**B.2 Event matrix**

| Event | Behavior |
|---|---|
| Missing file, GET | 404 `CONFIG_NOT_FOUND`. The UI uses `emptyAppConfigV2()`. The first save uses `If-None-Match: *` and writes v2 with no backup |
| Valid v1, any number of GETs | 200 with the migrated config, `storedSchemaVersion: 1` and the raw-byte ETag. No write; the upgrade notice shows |
| Valid v1, explicit save with the current ETag (profile add, edit or delete, or a defaults save) | Size check, then a byte-identical `.v1-<UTC>-<8hex>.bak`, then the atomic v2 replace. The notice disappears |
| Valid v1, stale ETag | 409 `CONFIG_CONFLICT`. No backup; unchanged |
| Valid v1 or v2 with the recovery header | 409 `CONFIG_RECOVERY_NOT_ALLOWED`. Unchanged |
| Create, Make another, a selection change, or a cancelled profile edit | No write; the profile's `reviewedOn` is unchanged |
| Profile add, edit or delete | PUT v2. Other profiles' `legacyChoices` and `defaults` pass through untouched |
| Save worksheet defaults | PUT v2 per DD9's defaults-save rule (D-save); `profiles` pass through untouched. Before Step 17 every worksheet group and the seeding flag pass through; from Step 17 it writes the visible selection with `useEarlierChildSettings: false`, so seeding ends permanently. Until Step 19, `theme` is derived from `useInterests` |
| Invalid file (bad UTF-8, bad JSON, or a v1 or v2 schema failure), GET | 409 `CONFIG_INVALID` with the raw ETag; the recovery panel shows |
| Recovery save | A byte-identical `.invalid-…bak`, then a replace with `emptyAppConfigV2()` plus the one draft profile. The panel stated beforehand what stays only in the backup |
| Integer `schemaVersion > 2` | 409 `CONFIG_VERSION_UNSUPPORTED` on GET, PUT and recovery. Never rewritten; the UI is blocked |
| An older build (Steps 1–13) meets a v2 file | Its own `> 1` rule blocks with `CONFIG_VERSION_UNSUPPORTED`; it never offers recovery |
| A stale tab running an older bundle PUTs v1 | 422 `VALIDATION_FAILED`. Unchanged |
| An upgrade whose v2 bytes exceed 65,536 | 413 `CONFIG_SERIALIZED_TOO_LARGE` from the store, or 413 `BODY_TOO_LARGE` if the request body itself exceeds Fastify's `bodyLimit`. No backup; unchanged |
| The upgrade backup cannot be created | 503 `CONFIG_IO_ERROR`. Unchanged |
| The upgrade backup is written but the atomic v2 replace fails | 503 `CONFIG_IO_ERROR`; the v1 target is unchanged and the `.v1-…bak` remains (no rollback, as for recovery backups today); the next successful save writes a second byte-identical `.v1-…bak` |
