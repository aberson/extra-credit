## 1. What This Feature Does

Proposal: documentation/printable-packets-proposal.html (plan-redline publication 1, 2026-09-29; a standalone offline view of this plan, which remains the source of truth)

A parent who has generated a worksheet can choose **Add to packet**, repeat with other worksheet types, variants and children, reorder or remove sheets, give one sheet new problems, preview the whole packet and print it once, with the answer keys placed where the parent chose (grouped at the end by default). It is built because the operator wants several sheets without generating and printing each separately (seed 03), and because printing is single-surface today: `PrintView` toggles one worksheet or one key and calls `window.print()` for that surface (`src/web/print/PrintView.tsx` :28-63), and the named `@page` comes from that surface's own paper (`print-letter.css` and `print-a4.css` :6-7).

Packets are **durable local drafts** (P4). The current packet lives in a second private, gitignored, versioned file, `config/packet-draft.local.json`, derived as the sibling of the config file the server already owns, with its own 256 KiB cap, strong ETags, preconditions, flushed atomic replacement, backup-first explicit recovery, release-export exclusion and privacy-audit coverage. Nothing packet-related touches browser storage. The config file keeps its 65,536-byte cap (`CONFIG_BYTE_LIMIT`, `src/server/config-store.ts` :16) and is never written by a packet action, so a restart restores the packet and never touches saved child profiles.

Each sheet stores **the already-generated immutable document** with exactly the problems and answers the parent previewed: request (seed and generator version included), worksheet id, items and answers. Only a packet layout change, or an Add at another layout, replaces a stored document, and only with the document its generator produces at the new layout with identical items (DD10); new problems come only from an explicit action (DD11). The file treats each document as opaque; on load the browser proves every sheet by regenerating it from its stored request and requiring an identical document (DD5). A sheet this version cannot reproduce is flagged on its own and is never silently replaced or reprinted. Changing controls, the selected child, a profile or the saved defaults can never change a queued page.

## 3. Scope

## 6. Design Decisions

**DD1. The packet stores the already-generated documents, opaque at file level (D9, D36).**
- **Stored per sheet:** `sheetId`, `profileId` and `document`, the generated `WorksheetDocumentV1` with exactly the problems and answers the parent previewed (Appendix A). A packet layout change, or an Add at another layout, replaces the document with the one its generator produces at the new layout with identical items (DD10); its request then names the packet's length, paper and scale. This is the D-packet deviation recorded in the Decision Inventory. The worksheet and its key both render from that one document, so they can never disagree.
- **Why documents:** the seed asks for them, and they keep what the parent previewed even when a later build cannot reproduce it: that sheet is flagged, never silently replaced, and its stored problems stay in the file until the parent removes or replaces them.
- **Size (D36):** at 5c22159 the largest document is 5,123 bytes compact, and ten of them make a 52,491-byte compact draft (106,206 pretty-printed). The draft is serialized compactly and capped at 262,144 bytes, and the PUT route gets that cap as its own `bodyLimit`; the global 65,536-byte limit and every config route stay. Step 28 requires the worst ten-sheet draft over every shipped family and every selection axis plans 01 and 02 ship (D47) to stay under half the cap.
- **Opaque at file level:** the envelope accepts any JSON object as `document` within a nesting depth of `PACKET_DOCUMENT_DEPTH_LIMIT` (64), measured iteratively, so no recursive serializer, canonicalizer or schema can overflow on a hostile file; Zod never walks the document (D54). A later request field, family, operation or generator change therefore never invalidates the file or forces a draft schemaVersion 2; it affects only the sheets it touches, through per-sheet verification (DD5).
- **Rejected:** a recipe plus a digest (a drifted sheet's problems would be unrecoverable, and the request type would enter the fingerprint, so every later request change would force a draft version); a strict per-family item schema (a second hand-kept copy of every item type, plan 02's included); a reference to the current controls (later control changes would rewrite queued pages).

**DD2. One current draft file beside the config (D10).**
- **File:** `packet-draft.local.json` in the directory of the config path the server was given (`packetDraftPathFor`). Production uses `config/packet-draft.local.json`; every harness gets a sibling inside its own `mkdtemp` directory, so tests, `manual:print` and the release smoke stay isolated and disposable, and `ephemeral-test`'s TEMP check covers it. The HTTP API never accepts a path.
- **Content:** one current packet (layout, placement, 0–10 sheets). Removing every sheet saves an empty `sheets` list; there is no delete route.
- **Rejected:** a key inside the config (its 64 KiB cap, strict schema and persisted-shape rule would force a config v3 and couple the two recoveries); several named drafts (the D10 tweak, through a draft schemaVersion 2).

**DD3. One file-safety core, two stores (D13).**
- **Why:** the config store's mechanics are private methods, and a second copy of safety-critical code would drift.
- **How:** Step 29 moves them into `src/server/local-json-file.ts`. `ConfigStore` keeps every export, type name, code, message and behavior, and its `load()` and `save()` bodies stay byte-identical, so plan 01's calibration anchor (the upgrade-backup statement in `save()`) is found exactly once, unchanged. `PacketDraftStore` is built on the same core in the same step, and one hostile-file parity table runs against both stores.
- **Matrix:** the packet store answers every state and precondition as the config store does, with its own codes (Appendix B); its one intended difference is DD4's missing-file read.
- **Rejected:** copying the mechanics; a generic store class parameterized by schema (a larger change to plan 01's store).

**DD4. API contract (D11, D12, D36).**
- `GET /api/packet-draft`: 200 `{ draft }` with the raw-byte ETag, or 200 `{ draft: null }` without an ETag when the file is missing. A missing draft is normal; a 404 would fail the release smoke's status and console checks (§2). Otherwise 409 `PACKET_DRAFT_INVALID` (ETag), 409 `PACKET_DRAFT_VERSION_UNSUPPORTED` (ETag), 409 `PACKET_DRAFT_TOO_LARGE`, 409 `PACKET_DRAFT_UNSAFE_FILE`, 503 `PACKET_DRAFT_IO_ERROR`.
- `PUT /api/packet-draft`: the whole draft; exactly one of `If-Match` or `If-None-Match: *`; the optional `X-Extra-Credit-Recovery: backup-and-replace` only against an invalid file; route `bodyLimit` `PACKET_DRAFT_BYTE_LIMIT`; 200 `{ draft }` with the new ETag.
- **Codes (D12):** 11 appended in this order: `PACKET_DRAFT_INVALID`, `PACKET_DRAFT_VERSION_UNSUPPORTED`, `PACKET_DRAFT_TOO_LARGE`, `PACKET_DRAFT_UNSAFE_FILE`, `PACKET_DRAFT_SERIALIZED_TOO_LARGE`, `PACKET_DRAFT_CONFLICT`, `PACKET_DRAFT_PRECONDITION_REQUIRED`, `PACKET_DRAFT_RECOVERY_NOT_ALLOWED`, `PACKET_DRAFT_IO_ERROR`, `PACKET_DRAFT_VALIDATION_FAILED`, `PACKET_DRAFT_CONTENT_TYPE_REQUIRED`. The subject-neutral shared codes `HOST_REJECTED`, `ORIGIN_REJECTED`, `CROSS_SITE_REJECTED`, `SESSION_TOKEN_INVALID`, `INVALID_JSON` and `BODY_TOO_LARGE` are reused. `VALIDATION_FAILED` and `CONTENT_TYPE_REQUIRED` are not, because their messages name the profile configuration, and no existing message changes. `CONFIG_*` codes are not reused, because App routes them to profile recovery and blocking, and the packet client converts every session-token failure into a packet code before it reaches the packet session (D49).
- **Anchors:** the route file holds exactly two `reply.header("ETag", stored.etag);` lines (the present-draft GET branch and PUT), the shape the calibration counts (Step 34).

**DD5. Per-sheet verification by regeneration (D14, D27, D29, D39).**
- **Rule:** a stored document is shown or printed only after `verifyPacketSheet` regenerates it from its own request, at its registered generator version and with its own worksheet id, and finds the canonical JSON of the whole document identical (Appendix A's ordered checks). The regenerated document is what renders. This proves every item, answer, invariant and key agreement without a hand-written item schema, and it cannot drift from the generators.
- **Bounded cost (D39, D54):** the envelope bounds each document's nesting depth before anything walks it, and checks 1–5 run before any generator. The strict request mirror bounds every numeric capability by its shipped ceiling, so a hand-edited or hostile draft cannot make verification enumerate a huge pool; a spy generator proves no generator runs for those outcomes.
- **Request mirror:** strict, transform-free and two-way type-checked against the shipped `GenerationRequestV1`, with bounds from shipped constants only. It includes plan 02's optional `practice` member as the shipped union and reuses a shipped schema wherever one states the same value domain, so no value rule is kept twice (D47, D55). `displayName` is checked by a refine that parses it through plan 01's profile field schema and requires the output to equal the input, so the transforming field schema is called, never embedded. Plan 02's facts and Number Bonds kinds are composed from plan 02's own `WorksheetSelectionV3Schema.shape.dryMathFacts` and `.shape.numberBonds` (or the field schemas plan 02 exports for them), extended only by the `kind` literal through Zod's refinement-preserving `.safeExtend()`, so plan 02's `factOperationsCanonical`, `factFamiliesAscending` and `numberBondsOperationsCanonical` rules run unchanged. Where a plan 02 schema cannot be reused as is (a refinement sits on an enclosing object, or its inferred array type is not readonly and would break the two-way check), the mirror keeps its own member, and an equality property over plan 02's boundary values requires that member and plan 02's selection member to accept exactly the same field values. The add-subtract kind's `regrouping` is the literal the shipped type declares. Optional members use `z.exactOptional()` and arrays `.readonly()`, because `tsconfig.shared.json` sets `exactOptionalPropertyTypes` (:9) and the shipped type declares readonly arrays, so the two-way check compares like with like. The mirror is a verification tool, not part of the persisted envelope, so it is not fingerprinted.
- **Where (D29):** the browser verifies at load. The server never runs generators; it checks envelope, size, file safety and preconditions, so a drifted sheet stays removable and repairable after an upgrade.
- **Per-sheet outcomes (D27):** a failed sheet is flagged on its own and blocks Preview and Print until it is removed or given new problems; the other sheets stay usable, and its stored bytes ride along unchanged on every save.
- **Rejected:** verifying on the server at every PUT (it would refuse edits to a packet holding a drifted sheet); making the whole draft invalid when one sheet fails (one drifted sheet would discard every queued sheet).

**DD6. The envelope is fingerprinted; the documents are not (D15).**
- `packet-draft-fingerprint.test.ts` pins the envelope's full value domain: the `z.toJSONSchema(PacketDraftV1Schema)` output (the envelope has no transforms), flattened into a sorted list of key-path strings so no committed object is keyed by the schema's property names (Document hygiene), the limit, depth and version constants, and the refinement names. It must pass unchanged at Steps 29–34 (S1).
- Any change to accepted envelope keys or values fails with "Changing the persisted packet draft shape requires packet draft schemaVersion 2 with a v1 read path", because an older build would otherwise classify a newer same-version draft as invalid and offer destructive recovery. `CONTRIBUTING.md`'s Persisted shape rule gains the draft in Step 28.
- Request, family and generator changes are deliberately outside the envelope and handled per sheet (DD5): a generator-version bump flags old sheets for new problems instead of orphaning the file.
- **Generator versions (D46):** plan 02 writes a Generator versions rule into `CONTRIBUTING.md` whose clause (1) keeps an old implementation registered while any stored document relies on it (A36). The registry holds one implementation per family and verification compares a document with that one version, so no old implementation could ever satisfy verification. Step 28 therefore amends clause (1): a bump flags every queued packet sheet made by an older version as `generator-version-unavailable`, keeps its stored bytes, and offers Remove or New problems; no old implementation is kept registered for packets. `packet-verify.test.ts` proves it with a registry injected one version ahead of the stored document.

**DD7. Privacy boundary before any writer (D16, D44, D45).**
- **Step 28:** two `.gitignore` lines, and `excluded()` drops any path part starting `packet-draft.local.json` anywhere, beyond the whole-`config/` rule.
- **Step 30:** `PACKET_RECORD` and `GENERATION_RECORD` (§4) with no allowlist; every fixture is built at runtime, every raw JSON body in a test is produced by `JSON.stringify` at runtime, and no generated sheet is ever committed (seed 03). Records built from the Zod schemas' own keys must fail, so renaming a schema key without updating a detector fails the suite.
- **What the draft holds (D45):** generated documents, which carry a nickname only when that worksheet prints one, reviewed topic ids and seeds, plus the profile id each sheet was made for. Requests carry no age (plan 01) and never free-text interests.
- **Step 34 (D44):** README, PRIVACY and SECURITY name the file, its contents and cleanup, and `BOUNDARY_DOCS` then requires the name; the calibration proves the browser gate fails on leaked sheet profile ids. Documentation lands with the finished feature, because interim documents are never pushed (P8).
- **Pre-run:** D-pregate is extended to the draft file (header item 1).

**DD8. The packet is the saved draft (D17, D18).**
- **Save before show:** every packet action computes the next draft with a pure transition, saves it with `If-Match` (or `If-None-Match: *` for the first save) and shows it only after success; a failed save changes nothing but the message.
- **One save in flight:** packet controls are disabled while a save is pending.
- **Conflict:** `PACKET_DRAFT_CONFLICT` reloads the saved packet once and says so; nothing retries automatically.
- **Undo (D18):** the last Remove, New problems or Make new problems for sheets … keeps, in memory, the exact saved draft from before that action and the ETag that action's own save returned. Undo is offered only while the session's current ETag equals that ETag, and it saves the previous draft with that `If-Match`, so it can never write into a packet another tab or another action has changed, and the restored draft is one that was already saved and verified. The slot clears on any other packet change, on any reload (a conflict reload, Retry, recovery or a page reload) and on any failed save, and is never persisted.
- **Token:** reads may refresh the shared session token and retry once; mutations are never replayed, as in the config client (`client.ts` :190-256).

**DD9. Adding a sheet (D19, D20).**
- Add appears only while the current preview is visible (plan 01 U7: plan 01 §5's worksheet session raises `previewEpoch` on every control change, child switch, config reload and profile change, never on a defaults save, and App clears the preview once per rise) and adds exactly that document with the selected child's profile id, the session state's `selectedChildId` (plan 01 §5, D-gap-session-reducer), which is always the child the visible preview was made for because a child switch clears the preview. It never reads the controls again and never writes the config or the saved defaults (P1).
- **Layout:** an empty packet adopts the document's paper and scale. Otherwise a document at the packet layout is added as is. From Step 32 a document at another layout is re-laid-out by DD10's rule, and the announcement names the packet layout and says its problems are unchanged (Appendix D), or it is refused with a remedy if its problems would change; Step 31 refuses any other layout (sequencing, non-destructive).
- **Refusals (D20):** an 11th sheet; a `worksheetId` already queued; items whose content key equals a queued sheet's stored items. Verification flags a duplicated `worksheetId` that only a hand edit could create.

**DD10. One packet layout that keeps problems (D21, D41).**
- **Rule:** `relayoutDocument` regenerates the sheet's request with only length, paper and scale replaced, keeping seed, generator version and worksheet id, trying the sheet's own length first and then the others, and accepts the first result whose content key equals the original's. The accepted document is a genuine generated document at the new layout, so verification and the proven single-sheet geometry both hold, and no renderer, print token or print file changes.
- **Why it keeps problems:** generators read length and scale only through their budgets and seed their randomness from the request seed (§2), so a page with the same allocation at the target scale reproduces the same items; Step 32 proves it per family. Paper is read by no generator, so a paper change keeps every sheet. At large print only pages longer than any large page (standard-scale Long Dry Math, Wow, Count/Compare and bank-mode Sentence pages) are named; a standard-scale Standard Dry Math sheet prints as the large Long page with the same 12 problems.
- **All or nothing (D41):** the layout applies to every sheet in one save or changes nothing; named sheets change only through "Make new problems for sheets …", which regenerates them in sheet order at the new layout (DD11) and applies the layout to all in one save that Undo covers (D18). If any named sheet gives `exhausted` or `failed`, nothing is saved: the draft, the layout and the Undo slot stay as they were, no request is sent, and Appendix D's batch copy names that sheet. A layout change is refused while any sheet is flagged.
- **Rejected:** rendering a document at a layout its generator would not produce (unproven geometry); requiring the same length (it refuses almost every scale change).

**DD11. New problems for one sheet (D22).**
- `regenerateSheetDocument` takes the sheet's stored request (never the current controls, child or profile), sets the registration's current generator version, draws up to `MAX_ALTERNATIVE_SEED_ATTEMPTS` nonzero seeds other than the current one, and accepts the first result whose content key differs from every queued sheet's, with a fresh worksheet id. Outcomes are `changed`, `failed` (the generator's message) or `exhausted`; the last two leave the sheet unchanged. In the batch action each accepted document's content key joins the key set before the next named sheet is regenerated, so no two regenerated sheets share items (D20).
- The sheet keeps its `sheetId`, position and `profileId`; its key changes with it because both render from the new document (K5). The nickname and topics are the ones the sheet was made with (K3, K9).
- A flagged sheet can get new problems when its family is registered and its stored request parses with the mirror. Before regenerating a flagged sheet, its request's paper size and print scale are set to the packet layout and its stored length is kept, so a `layout-mismatch` sheet comes back verified at the packet layout; otherwise it can only be removed.

**DD12. Composition, placement, labels and print CSS (D23, D24, D25, D42).**
- **Placement (D23):** `grouped-end` (default), `after-each-sheet`, `none` (Appendix C). A sheet has a key page exactly when its registration has `hasAnswerKey` and its request has `options.includeAnswerKey`.
- **Labels (D24, D42):** each key page's heading gains the sheet label, naming the sheet number, total and family, plus the nickname when that worksheet prints one, through `AnswerKeyView`'s optional `sheetLabel`, rendered as one `span[data-packet-sheet-label]` inside the existing `h2` only when the prop is present. Single-sheet markup is therefore unchanged, and every packet key page has a unique title for the PDF-outline oracle. Child pages render unchanged, because an added line on a maximum-length page would change geometry the single-sheet matrix proved; key pages do gain the label inside their heading, so Step 33 measures every labeled key page's headroom at maximum length and pre-authorizes one label-only remedy (D25); keys follow sheet order in every placement.
- **Key association (accepted limitation, D24):** a child page's title is its family title plus the nickname when one prints, so under grouped placement two keyed sheets of one family whose printed nickname is equal, or absent on both, print identical child titles whichever children they were made for, and their keys match their child pages only by order and by problem content; some keys (Wow choices, Count, Compare & Make answers) print no source expression. Whenever two keyed sheets share `worksheetType` and an equal `request.displayName` (both absent counts as equal), regardless of `profileId`, the answer-key group shows Appendix D's same-title note recommending Each key after its worksheet, which pairs every key with its page; a child's sheets that differ in whether the nickname prints get no note. The parent's saved placement is never changed automatically. If a later renderer adds more to its title, this rule can only over-trigger, never miss an ambiguous pair. M1 and M2 observe it. The redline alternative is an optional label inside each renderer's title heading, proven by a sweep over every web renderer that markup without the prop is unchanged and by a re-run of the print matrix.
- **Print (D25):** one `.print-surface` per page inside one packet `.print-workspace`, which replaces the single preview while open, so exactly one print workspace is mounted and the existing strict `.print-surface` locators never see two. `print-packet.css` is imported statically (bundled at startup, guarding Step 10's delayed-CSS failure class) and adds only `break-before: page` for every packet surface after the first, plus screen spacing and, only if Step 33's key headroom check needs it, one rule for `[data-packet-sheet-label]`.
- **One print:** "Print packet" calls `window.print()` once; preview, print and cancel send no request and never change the packet.

**DD13. Two stores, no coupling (D38).** Neither store reads, locks, backs up or classifies the other's file, and backups carry distinct prefixes. A damaged, newer, oversized or unsafe draft blocks only packets: profiles, generation and single-sheet printing keep working. A damaged config shows profile recovery and leaves the draft byte-identical. A restart is a new `buildApp` over the same two files and changes neither. Step 30 proves the whole state matrix, including the first explicit save of every committed legacy config fixture (plan 01's v1 and plan 02's v2, each writing its own upgrade backup), with a mirror case.

**DD14. Visibility, test infrastructure and hygiene (D28, D30, D31, D32, D33, D37).**
- **Visibility (D28):** the packet panel renders only while the draft holds a sheet or needs attention. Needs attention means the session is `recovery`, `blocked` or `unavailable`, its Undo slot is non-empty (DD8), or a packet message is pending (a failed save, a conflict reload, or an announcement such as Removed sheet {n}.) until the next packet action or a reload replaces it; so removing the only sheet keeps its announcement and Undo visible, and a failed first Add shows its message. The empty first screen and plan 01's relocated 1920×1080 test are unaffected, because neither holds a sheet, an Undo slot or a message, and that test runs on the ephemeral compiled fixture whatever stray draft the main checkout holds.
- **Helpers (D33, D57):** every packet interaction in specs goes through `tests/e2e/fixtures/packet-controls.ts`; seeds are injected through `tests/e2e/fixtures/seed-stub.ts` and packet surface content is read through `tests/e2e/fixtures/packet-print-content.ts`, copies of `print.spec.ts`'s module-private stub and reader, which S4 keeps frozen; drafts are seeded through `appServer` packet accessors with documents built at runtime; `backupContents()` narrows to config backups. The accessors, the narrowing, the release-smoke edits and the App-level fetch-mock helper land in Step 30 with the route, so the UI steps carry no test-infrastructure edits.
- **Spec names (D37):** no packet spec name ends in `print.spec.ts`, so `ci-contract.test.ts`'s unanchored filter keeps counting only the single-sheet matrix; the evidence spec gets its own pin.
- **Page-order evidence (D32):** two independent oracles. Step 33: the composed DOM order with the PDF page count, calibrated in the same spec, plus geometry equality with the single-sheet render in one cell. Step 34: the PDF outline read with `pdf-lib`, whose titles are unique because each evidence sheet has its own runtime-built nickname and every key heading carries its sheet label, calibrated by swapping two Sentence Builder surfaces and two key surfaces.
- **Titles:** titles, step names and logged text avoid example ids, nicknames and interest words even as substrings ("workspace" contains one); plan 01's `e2e-title-privacy.test.ts` checks titles.
- **Smoke (D30):** a single-test Playwright project keeps the calibration's "1 passed" oracle exact.
- **Evidence (D31):** `documentation/printable-packets-evidence.md`; DONE never depends on what a reviewer chooses to do (D-scripted-evidence).

### B. Packet draft store and API event matrix

| Event | Behavior |
|---|---|
| Missing file, GET | 200 `{ draft: null }`, no ETag; the panel stays hidden until a sheet is added |
| Missing file, PUT with `If-None-Match: *` | Create with an atomic write, mode 0600; no backup |
| Missing file, PUT with `If-Match`, or with the recovery header | 409 `PACKET_DRAFT_CONFLICT`, or 409 `PACKET_DRAFT_RECOVERY_NOT_ALLOWED` |
| Valid file, GET | 200 `{ draft }` with the raw-byte ETag; a read never writes |
| Valid file, PUT with the current `If-Match` | Size check, then atomic replace; 200 with the new ETag |
| Valid file, stale `If-Match` | 409 `PACKET_DRAFT_CONFLICT`; unchanged; the client reloads once |
| Valid file, PUT with `If-None-Match: *` in place of `If-Match` (a second tab's first save) | 409 `PACKET_DRAFT_CONFLICT`; unchanged; the client reloads once (with the recovery header, `PACKET_DRAFT_RECOVERY_NOT_ALLOWED` comes first, the config store's order) |
| Valid file, recovery header | 409 `PACKET_DRAFT_RECOVERY_NOT_ALLOWED`; unchanged |
| No precondition, both, or an empty `If-Match`, in any file state | 428 `PACKET_DRAFT_PRECONDITION_REQUIRED`, before the file is read |
| Invalid file (bad UTF-8, bad JSON, envelope failure, a document deeper than `PACKET_DOCUMENT_DEPTH_LIMIT`), GET | 409 `PACKET_DRAFT_INVALID` with the raw ETag; the recovery panel shows |
| Invalid file, PUT with its current `If-Match` and no recovery header | 409 `PACKET_DRAFT_RECOVERY_NOT_ALLOWED`; unchanged |
| Invalid file, PUT with a stale `If-Match`, or with `If-None-Match: *` in place of `If-Match`, with or without the recovery header | 409 `PACKET_DRAFT_CONFLICT`; unchanged (the config store's order: the precondition is checked before the header) |
| Invalid file, recovery PUT with its ETag | Byte-identical `.invalid-` backup (`wx`, 0600, fsync, at most eight attempts), then the atomic replace with the body (the client sends an empty draft) |
| Integer `schemaVersion` above 1 | 409 `PACKET_DRAFT_VERSION_UNSUPPORTED` with ETag on GET, PUT and recovery; never rewritten; packets blocked |
| More than 262,144 bytes on disk | 409 `PACKET_DRAFT_TOO_LARGE`; never read, hashed or recovered through the app |
| Symbolic link, non-regular target, or `dev`/`ino` swap | 409 `PACKET_DRAFT_UNSAFE_FILE` |
| Serialized draft over the cap | 413 `PACKET_DRAFT_SERIALIZED_TOO_LARGE`; no backup; unchanged |
| Request body over 262,144 bytes | 413 `BODY_TOO_LARGE` (the config route keeps its 65,536-byte limit) |
| Backup or replace fails | 503 `PACKET_DRAFT_IO_ERROR`; target unchanged |
| Body not `application/json` | 415 `PACKET_DRAFT_CONTENT_TYPE_REQUIRED` |
| AJV or Zod failure, a document deeper than `PACKET_DOCUMENT_DEPTH_LIMIT` included | 422 `PACKET_DRAFT_VALIDATION_FAILED` (Zod failures carry `fieldErrors`); a body too deep for the JSON parser gives the shared 400 `INVALID_JSON`, never 503 |

| Any packet request | The config file is never read or written |
| Any config request, including config recovery and the first explicit save of any legacy config version (plan 01's v1 and plan 02's v2, each writing its own upgrade backup) | The draft file is never read or written |
| Add, remove, move, undo, new problems, layout or placement change | One PUT of the whole next draft, shown only after success; Undo PUTs the previous saved draft only while the saved ETag is the one its action produced |

| A sheet fails verification at load | That row is flagged; the file is unchanged; Preview and Print wait until it is removed or given new problems |
| A build from before this plan | Never reads the draft file; unaffected |

### C. Print composition

`composePacketPages(sheets, placement)` returns pages in this order. `W(n)` is sheet n's worksheet page and `K(n)` its key page; `K(n)` exists only when the sheet's registration has `hasAnswerKey` and its request has `options.includeAnswerKey`.

| Placement | Label in the panel | Page order |
|---|---|---|
| `grouped-end` (default) | All answer keys at the end | W(1) … W(N), then K(n) for each keyed sheet in sheet order |
| `after-each-sheet` | Each key after its worksheet | W(1), K(1) if any, W(2), K(2) if any, … |
| `none` | Leave out answer keys | W(1) … W(N) |

Every page is one `.print-surface` at the packet layout, and every key page's heading carries its sheet label (DD12). Every page after the first starts a new printed page, each fits one printable page (proven at maximum length in Step 33), and no key shares a child-facing page. Child pages are rendered exactly as a single sheet.
